2.0 CEO 先看：这周对产品实际带来了什么

用一句话概括：Server 侧已经把“录到一段原始屏幕视频”推进为“拿到一份可追溯的演示结果，并能在本地工作台继续剪辑、加字幕、配音和导出”的产品闭环；同时为下一阶段的 Browser Agent 打好了协议与安全边界，但它还没有成为可自主纠错的生产 Agent。

演示不再止于录屏录制完成后，视频、关键截图、执行轨迹和结果说明可以作为一份结果交付；用户不必从零整理素材。
用户可继续编辑成片录屏可进入本地视频编辑页，支持裁剪、分割、排序、静音/调音量、字幕、配音和预览/导出；原始素材保持不被改写。
问题可以被定位包体、录制、渲染和交付失败开始被分开记录，并可带回截图、轨迹和原因；团队不再只能看到“任务失败”。
下一阶段已有跑道App 与 Server 已约定 Browser Agent 的输入、不可修改边界和结果格式；下一步重点是让它真正执行并在小范围内自修复。
CEO 会关心的问题现在可以怎么回答实际体验/商业意义当前不能夸大的地方
我们现在能展示什么？可以演示：Server 接收一份测试执行包，完成本地录制并生成视频/截图/结果信息；随后在 127.0.0.1:3000 的视频编辑页打开素材，手动整理成演示视频。客户或内部同事能看到从“执行任务”到“可编辑 Demo”的连续体验，而不是一堆分散文件。这是本地/开发环境的闭环；真实最终导出依赖安装并配置 FFmpeg。
这周最大的用户价值是什么？把一次执行的成果保留下来，并让用户能直接处理，而不是录制失败或效果不佳后完全重来。减少重复录制和人工找素材的时间；关键步骤截图还能作为讲解画面补充到视频中。编辑器只允许已验证的剪辑、字幕、音频等操作；尚未承诺复杂特效、自动美化或任意 AI 改视频。
如果页面按钮位置变了，系统会自己解决吗？现在的旧录制路径可按既定步骤稳定执行；新 Browser Agent 的“识别相近按钮、修正定位、小问题后继续”能力已经完成协议设计和输入校验。团队已经明确将来可自动处理哪些“小偏差”，哪些必须停下来报错，避免 Agent 自作主张改业务流程。还不能说已具备自主纠错能力。真正的 Outline Runner、定位器、结果验证和修复账本仍在下周 P0/P1 开发范围内。
音频 AI、自动字幕能马上商用吗？用户上传/录入音频后的时间线、配音和字幕导出入口已预留；豆包 LAS/TTS 的接入资料与安全适配层已准备。后续接入识别、配音、降噪或变声时，可以接进现有编辑流程，不需要重做时间线和 Renderer。还没有开启真实厂商调用。在真实凭据、音频上传地址和请求/响应验收完成前，只能 dry-run，不向用户承诺识别效果或调用时延。
客户数据和账号安全吗？当前已做到包体预检脱敏、凭据引用化、结果中避免回传明文敏感信息，并完成生产隔离的设计。从设计起避免把密码、cookie、完整页面源码等不必要数据塞进执行包和诊断包。生产级隔离尚未上线。每任务容器/MicroVM、强制网络出口、Vault 等需要下一阶段基础设施落地，当前不能用生产凭据进行对外承诺。

目标不是同时把“智能 Agent、生产隔离、音频大模型、编辑器效果”全部做完，而是先让最新 Outline 协议在 Server 本地形成一个可执行、可诊断、可回归的最小闭环。App 侧无需停工：Server 先使用已有 official fixture 和稳定的三合一包推进。

让 Outline 包真正进入 Server 执行链

实现 Runtime Router 与最小 BrowserAgentOutlineRunner：识别 browser-agent-outline-v1，允许空的 playwright_script.inline_source，把 stage_approval_plan、script_outline、合同和最终策略装配为按 node_id 顺序运行的 stage request。Legacy Playwright 路径必须保持回归兼容。

三、协议主线与架构判断

新主路线不是“App 生成最终 Playwright TS，Server 机械执行”，而是“App 生成可审批路线图，Server 在不可变业务合同内自适应执行”。

必须如实区分：当前 Server 已能接收并校验 Outline 包；但执行流水线仍默认走 playwright，Worker 会将空 playwright_script.inline_source 视为错误。因此 Outline 运行时尚未可用，不可对外宣称 Browser Agent 已完成。

七、Server 侧工程格式与责任边界风险

格式与一致性风险

  • runtime 不匹配：browser-agent-outline-v1 不得要求内联 TS；当前 Worker 仍会报 script_missing。
  • hash 不一致：Plan、Stage Plan、Outline、Prompt Policy、Contract、Markdown、Bundle 必须用稳定 canonical JSON / UTF-8 SHA-256。
  • 节点错位：Graph、Stage Plan、Outline 必须按 node_id 一一对齐，不允许漏阶段或私自插阶段。
  • 时间语义错误：只保留用户明确给出的时长；不能给所有步骤写死 10 秒或 60 秒。
  • 状态语义错误：上传失败不得覆盖 App 本地规划状态；执行失败必须区分 selector、合同、录制、渲染与 checksum。

安全与运行边界风险

  • 秘密：包体、日志、trace、诊断中只允许 secret_ref，不得出现密码、token、cookie、Authorization、storage 内容。
  • 控制面隔离：/aigc、/.well-known、/v1、执行包与结果包接口不能成为产品探索路径。
  • 业务事实：页面现实与批准阶段目标冲突时必须 stop_and_report，不能“找一个看起来能点的按钮”继续。
  • 修复范围：只允许 selector、等待、截图时机、同域非破坏性探索、frame resolution；禁止改输入语义、stage 顺序、业务目标与 destructive 标记。
  • 生产隔离：当前 Cloud/MicroVM driver 仍是骨架，生产执行不能直接等同于本地 Node Worker。

八、两人分工建议与责任边界

同事：App 侧业务理解与包体生产

  • 对“要演示什么、阶段顺序、业务输入、成功标准”负责。
  • 维护代码调研、Business Stage Plan、Graph、RunSpec、三件套、审批 UI 与包体 hash。
  • 提供 target_contract、证据引用、允许域名、禁止页面、capture 语义。
  • 对包体 schema、fixture、审批结果和上传/轮询体验负责。
  • 不承担运行时 selector 修复；不要求其为 Server 生成最终 TS。

我们：Server 侧 Browser Agent 与结果交付

  • 对 Intake、Sandbox、secret_ref、运行时策略守卫、执行、录制、诊断、渲染、结果包和本地编辑导入负责。
  • 在合同允许范围内修复 selector / wait / capture timing，并永久记录 patch ledger。
  • 对成功/失败分类、trace、脱敏、checksum、下载与 ack 负责。
  • 不得推断或改写业务意图、输入值、阶段顺序和安全策略。
  • 本地视频编辑器继续消费 Server 结果素材，不改变 App 的业务真相。

十一、Server Intake 错误归属与生产隔离说明

结论：Intake 是“验收门”，不是“替 App 改业务包”的服务。Server 必须把可诊断的校验错误结构化返回；只有包已验收后、且 Browser Agent Contract 明确授权的运行时机械修复，才可由 Server 自动执行并留痕。生产隔离不能依赖提示词，必须由基础设施和运行时强制执行。

10.1 Intake 返回错误后，谁负责修改？

错误/事件类别Server 的动作最终由谁修复是否允许 Server 改执行包
包体事实或审批不一致
schema、必填字段、node_id、hash、签名、runtime、域名、沙箱策略、审批元数据		拒绝上传，不创建可执行任务；返回稳定的 code / field / reason / hint，例如 bundle_hash_mismatch。App 侧重新生成三合一包、重算 hash；若业务内容改变则重新审批。不允许。Server 改一个字节都会使审批内容与 hash 失真。
上传会话、网络、认证或服务端暂态故障保留本地规划与已接受状态；按幂等键重试，或要求重新 init 后上传。错误须和“本地规划失败”分开标识。Server 负责修复基础设施；App 仅在会话过期时按提示重新发起上传。不改业务包；相同有效包可重试。
已接受后的机械执行问题
selector 失效、等待不足、截图时机、同域非破坏性定位路径		仅在 browser_agent_contract 与 Repair Policy 授权范围内尝试修复，记录每次 observation、patch、置信度和验证结果。Server Browser Agent。可改运行时 patch，不能改原包。必须写入 patch ledger，并绑定原始 node_id。
业务或安全冲突
目标控件语义不一致、输入含义/阶段顺序冲突、越过 allowed domain 或 forbidden page、破坏性动作		stop_and_report；生成脱敏失败诊断、截图/trace 引用和 repair_request。App 侧更新业务路线与审批材料后重新上传；Server 侧只修复自身平台故障。绝不允许。

这里的关键边界是：Intake 的结构化错误是“让 App 知道哪里不符合协议”，不是“让 Server 猜测并篡改已审批的业务事实”。运行时 patch 只是一份附加账本，不覆盖原始三合一包。

10.2 生产凭据与执行环境应如何隔离

包体与控制面

  • 包体只出现 secret_ref / grant 引用
  • 密文 payload、签名、digest
  • 不传密码、token、cookie、.env
  • 结果只返回脱敏 artifact ref
→

Secret Broker / Vault

  • 校验引用、用途、域名与有效期
  • 以 job identity 读取短期凭据
  • 仅注入本次运行的受限 context
  • 运行结束撤销、轮换或删除
→

每任务隔离 Worker

  • MVP：per-job container
  • 高风险/企业：per-job MicroVM
  • 只读根文件系统；仅 /workspace、/tmp 可写
  • 无 host mount、无 Docker socket、CPU/内存/磁盘/超时上限
→

浏览器与交付

  • 每任务 fresh browser context
  • 扩展与下载禁用
  • 强制 egress proxy、DNS/IP 防护、域名白名单
  • trace/截图脱敏、加密、checksum、有限保留期
防线应由什么来强制当前代码事实生产判定

不要把“策略存在”误当成“生产隔离已完成”。当前 mvp_cloud 与 enterprise driver 会明确返回“not implemented”；本地路径是 Node Worker + Playwright。提示词不是安全边界，真实的 Vault、网络和计算隔离需要在 Server 基础设施层落地并做攻击面测试。

10.3 建议的生产实现：一个任务 = 一个短生命周期的隔离执行单元

下面是 Server 侧应实际执行的链路。重点不是“给 Agent 一段不要越权的提示词”，而是即使 Agent、网页或 Worker 被攻破，也没有宿主机权限、没有长期凭据、不能绕过网络出口，且任务结束后环境会被销毁。

1. 接收与准入

Intake 校验签名、hash、审批、合同、域名和引用；把 App 提交的约束与 Server 生产基线取交集。

effective_policy = server_baseline ∩ package_policy ∩ contract
2. 创建隔离任务

Server 只向调度器提交 job_id、加密 payload ref、policy hash 和短期工作负载身份；不把真实凭据写入任务参数。

per-job container / MicroVM
3. 受限执行

Worker 在独立环境内启动浏览器、执行 Outline；网络只能经出口代理，文件只可写临时工作区。

fresh context + allowlist
4. 受控取密

Worker 按 secret_ref 向 Broker 请求本任务、当前节点允许的短期凭据；值直接用于填表，不进入模型上下文、日志或 trace。

Vault + workload identity
5. 交付与销毁

产物先脱敏、加密、checksum 后上传；关闭 Context，撤销租约，删除临时目录并销毁 container / MicroVM。

audit + TTL cleanup
实现环节Server 应如何具体实现必须验证的结果
策略裁决（不能信任包体自报）Server 保存一份不可由 App 覆盖的生产基线：强制 mvp_cloud 或 enterprise profile、每任务隔离、禁止 host mount / Docker socket、必须 proxy、只读 rootfs、Vault-only。App 包只能进一步收紧 allowed domains、时限或修复权限，不能放宽 Server 基线。将最终的 effective_policy canonicalize、hash，并记入审计和结果包。恶意或错误包即使声明 local_sidecar、无限网络、host mount，也会在准入阶段被拒绝；Worker 收到的是 Server 计算出的最终策略。
计算隔离MVP：用任务调度器启动一个非 root 的 per-job 容器（例如 Kubernetes Job / 托管批处理任务），设 readOnlyRootFilesystem、runAsNonRoot、移除 Linux capabilities、seccomp/AppArmor、禁止 privileged 与 hostPath；只挂载 tmpfs/临时卷到 /workspace、/tmp，设 CPU、内存、磁盘和超时上限。
企业/高风险：把同一 Worker 镜像运行于 per-job MicroVM（如 Firecracker 类隔离），而不是仅普通容器。		Worker 无法读取 Server 文件、宿主机目录、Docker socket 或其他任务工作区；超时/超配额会被平台终止；销毁任务后不存在可复用浏览器 profile。
网络隔离集群/宿主机网络默认 deny-all。执行单元仅可连接内部 egress proxy；proxy 负责解析 DNS、核对 FQDN allowlist、拒绝 loopback/link-local/RFC1918 等保留 IP、阻止 DNS rebinding，并只放行产品域名、必要的 Vault/产物端点。Playwright 的 page.route 域名拦截保留为第二层，不可作为唯一防线。即使网页脚本试图访问 169.254.169.254、内网服务或非允许域名，也会在网络层被拒绝；proxy 日志只记录脱敏元数据。
凭据隔离Job 通过 workload identity 取得调用 Secret Broker 的短期身份；Broker 根据 job_id + node_id + secret_ref + effective_policy 判定是否允许。凭据以一次性/短租约形式仅驻留 Worker 内存，并由受限接口完成 fillSecret(locator, secret_ref)；Browser Agent 的 LLM 提示词、环境变量、JSON-RPC、控制台日志、trace 和结果包均不得获得明文。任务结束即 revoke/rotate/delete lease。包体、数据库、日志和 failure diagnostic 均只有 secret_ref；不存在长期 AK/SK、密码或 cookie；越权引用或过期租约不可读取。
浏览器与运行时Worker 启动无持久 profile 的浏览器，每次只建一个 fresh Context，禁扩展、禁下载、禁任意 shell / Node 子进程。Action Executor 只暴露经过 Policy Guard 检查的 navigate / click / fill / select / wait / capture 等白名单动作；模型只能提出候选动作，不能直接拿到 OS、网络、文件或 secret API。任务之间没有 cookie、localStorage、缓存或下载文件串用；模型越权调用不会进入真实执行器。
产物、审计和清理截图前按 mask selectors 脱敏；禁止全文 DOM、请求头、cookie 和 storage 导出。Worker 用仅可上传本 job 路径的短期 token 将产物交给 Artifact Service；服务端进行 checksum、敏感标记和按接收方公钥/信封密钥加密。最后关闭 Context、回收临时卷、销毁执行单元，并写入 policy hash、worker/container/VM id、secret lease 已撤销和 cleanup 状态。结果包可追溯、可验证而不泄密；即使保留 trace，也不包含原始凭据；清理失败会被标记为安全事件而不是静默成功。

推荐技术路线：先把 CloudDriver 实现为“提交并监控 per-job container”的调度适配器，再接 SecretProvider / Secret Broker 与强制 egress proxy；企业级再把该调度接口替换为 MicroVM provider。这样 Browser Agent、结果包和编辑器不需要重写，只替换其下方的安全执行底座。
