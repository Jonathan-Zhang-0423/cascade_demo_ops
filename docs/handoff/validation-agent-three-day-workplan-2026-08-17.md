# Server Validation Agent 三日开发任务说明

## 目标

把 Validation Agent 提升为 Server 端到端验收的独立质量门：能够发现问题、保留充分证据、还原失败现场，并给出可执行且责任边界明确的修复建议。

本任务的成功标准不是让验收“更容易通过”，而是让每次通过或失败都可复核、可重放、可归因。

## 范围与边界

负责范围：

- ClientExecutionPackage、阶段事件、StepResult、截图、Trace、录屏索引和结果包的一致性验证。
- 动作前条件、动作后业务结果、目标几何和截图证据之间的关联验证。
- 失败分类、证据索引、现场重放清单和面向 App/Server 的修复建议。
- 离线回归夹具、单元测试和端到端结果包的验证报告。

不负责且不得修改：

- App 产包规则、前端代码、原始执行包、哈希或审批结果。
- Browser Agent 的页面操作、凭据处理和 Chromium 录制实现。
- 视频编辑器、渲染器、TOS、Seedance、TTS、模型适配或模型输出采用策略。
- 为让验证通过而放宽安全、证据、审批或执行规则。

所有新增验证结果必须将 `original_package_unchanged=true` 作为前提；测试夹具、waiver 和 mock 结果不得标记为正式 App 到 Server 联调成功。

## 第一天：证据闭环与失败分类

### 实现

1. 建立 `ValidationRunReport v1`：按 `package_id`、`bundle_hash`、`plan_hash`、`run_id` 和 `stage_id` 汇总验证结论。
2. 对每个阶段强制关联：动作定义、动作前截图、动作后截图、StepResult、阶段事件时间线和 Trace 引用。
3. 建立稳定的失败分类：
   - `app_package_contract`：字段、selector、evidence、需求映射或审批缺失；
   - `server_execution`：执行、目标解析、运行时副本或结果收集错误；
   - `browser_runtime`：页面导航、元素不可见、会话过期、超时；
   - `media_evidence`：截图/录屏/几何/时间轴缺失或不一致；
   - `provider_candidate`：仅针对候选模型任务，不影响真实页面业务证据；
   - `environment`：端口、网络、工具或本地依赖问题。
4. 每条失败必须包含：机器可读错误码、责任域、阻断级别、证据路径或 artifact ID、可复现条件、推荐修复动作。

### 交付

- `validation_run_report.json` 示例及 JSON Schema/字段说明。
- 至少 8 个单元测试，覆盖成功、缺截图、哈希不一致、动作后验证错误、会话过期、selector 冲突和环境错误。
- 一份失败分类对照表，供 App 与 Server 使用相同口径。

### 验收

任一阶段失败时，报告能够在不读取密码、Cookie、Token 或 API Key 的前提下定位到具体 stage、具体证据和责任域。

## 第二天：现场还原与语义验证

### 实现

1. 建立 `ReplayManifest v1`，按时间排序列出复现一个阶段所需的：目标 URL、非敏感视口信息、阶段输入引用、截图、录屏时间区间、Trace、验证结果和环境摘要。
2. 实现“动作目标与结果目标分离”验证：
   - 点击按钮的目标，不能被同时用作“弹窗已打开”或“构建已完成”的证据；
   - fill 必须有输入值引用及动作后 value/业务状态证据；
   - 动态路由必须使用捕获到的真实 ID 或受约束模板，不能把 `:id` 当字面 URL。
3. 实现目标几何一致性检查：若存在 `target_geometry`、高亮框或 cursor 证据，验证其 viewport、截图尺寸和目标 artifact 是否一致；不一致时只报错，不修改编辑计划。
4. 为候选 selector 修复增加二次验证要求：只能使用原包已批准的候选字段；必须记录原 selector、候选 selector、Evidence ID、实际命中数和动作前后证据。

### 交付

- `replay_manifest.json` 示例和生成器。
- 语义验证规则及至少 10 个回归用例。
- 一份可直接打开的失败现场索引，能从报告跳转到对应截图、日志和阶段记录。

### 验收

对“新建项目”这类动作，报告必须能明确区分“按钮已点击”“创建弹窗可见”“名称已写入”“构建已启动”“构建完成”，禁止用前一状态替代后一状态。

## 第三天：端到端验收门禁与开发反馈

### 实现

1. 把 ValidationRunReport 接入现有 Server 结果包，使每轮验收同时生成：总览、阶段结论、失败分类、ReplayManifest 和修复建议。
2. 建立发布门禁：
   - 正式验收仅接受 App 正式原包、有效审计、完整哈希和通过的安全/证据门禁；
   - test waiver、fixture、mock、离线编辑结果必须显示 `not_formal_app_server_success=true`；
   - 模型候选成功不能替代业务动作成功。
3. 建立自动反馈格式：将 App 侧问题与 Server 侧问题分开输出，避免把运行环境、模型候选或 Server 缺陷错误归因给 App。
4. 选择一份历史失败包和一份 Server-controlled 成功夹具运行回归，证明报告在失败和成功两种路径均可生成且字段稳定。

### 交付

- 端到端验证报告接入代码与测试。
- 历史失败包的重放报告一份。
- Server-controlled 成功夹具报告一份，并明确标记其非正式性质。
- 开发反馈模板：`app_feedback.md` 与 `server_feedback.md`。

### 验收

一轮验收结束后，开发者无需人工翻找大量日志，就能回答：失败在哪个阶段、为什么失败、由谁负责、依据什么证据、如何复现、最小修复是什么。

## 协作接口

输入来自 Server 的不可变执行包和运行产物；验证模块只读取，不改写。输出只作为验收结论、调试反馈和发布门禁依据。

涉及以下问题时必须先提报，不自行改动：App 协议字段含义、审批语义、模型候选采用规则、视频编辑逻辑、TOS 或 TTS 凭据、真实页面操作策略。

## 提交要求

- 每日独立提交，提交信息说明验证规则、测试覆盖与不影响的边界。
- 不提交 `.env`、密钥、Cookie、录屏中的敏感原件或临时签名 URL。
- 提交前运行相关 Go/Node 测试，并在说明中列出通过/跳过项。
