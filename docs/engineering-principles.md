# 工程与 Agent 设计原则

这份文档是 Cascade DemoOps Engine 的长期工程准则。它约束架构设计、Agent 设计以及日常执行过程；具体协议、schema 和已批准的架构决策仍是更具体的事实来源。

## 核心准则

> 把不确定性隔离，把边界和决策显式化，把失败设计成可恢复，把结果设计成可验证。

## 软件架构

1. 为变化设计：隔离易变部分，保持稳定核心简单。
2. 高内聚、低耦合：模块职责单一，通过最小化接口协作。
3. 边界优先：先定义领域、数据所有权、依赖方向和契约，再选技术。
4. 契约显式：API、事件、错误、权限、版本和兼容策略都要可检查。
5. 核心依赖抽象，不依赖具体数据库、队列或厂商 SDK。
6. 没有真实规模或可靠性需求时，避免过早分布式化。
7. 把超时、重试、幂等、熔断、降级、补偿和死信作为正常设计路径。
8. 明确一致性取舍，并为异常状态提供修复路径。
9. 从一开始设计日志、指标、链路追踪和审计。
10. 默认最小权限、输入校验、密钥隔离和数据脱敏。

## Agent 设计

1. 为 Agent 明确目标、权限、工具范围、预算、时限和禁止事项。
2. 输出必须可测量、可验收；不能只要求“完成任务”。
3. 工具少而专，参数和错误清晰，避免万能工具。
4. 分离读取、计划、执行和验证；分离事实、推测和待确认事项。
5. 区分短期上下文、任务状态、长期记忆、外部事实和临时草稿。
6. 副作用操作必须幂等、可审计；高风险操作必须人工确认。
7. Agent 可以拒绝、暂停或升级，不得用猜测填补关键事实。
8. 用正确率、完成率、成本、延迟、安全性和可恢复性评价 Agent。

## 执行过程

1. 先定义结果和验收标准，再拆解步骤。
2. 先调查再决策，先用低成本实验验证关键假设。
3. 小步、可逆、频繁验证；每次变更保护既有不变量。
4. 根据新证据更新计划，不机械坚持原方案。
5. 自动化重复检查，人工判断高风险取舍。
6. 每项任务设置完成、失败和升级条件，防止无限循环。
7. 失败保留证据；复盘必须转化为测试、监控、约束或文档改进。

## 评审问题

- 这项变更解决了什么问题，边界和不变量是什么？
- 如果依赖失败、输入异常或 Agent 判断错误，系统如何表现？
- 结果如何验证，失败如何恢复，操作如何审计？
- 是否引入了不必要的复杂度、权限或不可逆副作用？
- 是否有足够的测试和运行证据支持“完成”的结论？
