一句话定位

Cascade DemoOps Server 是把 App 侧已理解、已编排、已审批的产品演示意图，安全地执行在真实页面上，并生成经过结果验证、可编辑、可追溯的视频交付物的执行与媒体控制面。

我们的差异不是“能自动点击网页”，而是把协议校验、执行授权、真实页面证据、Outcome Verifier、受控修复和视频结果绑定成一条可信链路。

输入

版本化 Exchange Envelope、Client Execution Package、审批与安全策略、业务动作和结果契约。

输出

Recording Result Package、步骤结果、验证报告、审计事件、失败诊断、素材目录和最终视频。

核心价值

将不稳定网页自动化变成边界清晰、失败可解释、结果可验收的生产流水线。

Server 不做什么

不替 App 发明业务目标，不绕过审批，不保存明文凭据，不用剪辑掩盖执行失败。

App 交付之后：Server 的端到端责任链

1

建立可信传输

通过安装配对和会话身份确认发送方；协商公钥、加密套件、压缩、大小和有效期。生产路径只接受加密 payload reference，不把明文执行包当作普通请求体。
↓
2

Intake 与协议校验

校验 Schema、包类型、组织/项目、签名、摘要、nonce、防重放、TTL、幂等键、附件引用、审批字段和来源绑定。不合格时返回机器可读错误及修复建议。
↓
3

运行时计划编译与路由

根据 script_manifest.runtime 选择执行器；把 Browser Agent Outline 编译为 Server 可执行 Stage，并校验允许域名、来源、路由、禁用页面、敏感字段和资源上限。
↓
4

隔离执行与证据采集

在独立浏览器上下文中执行动作，记录阶段事件、动作前后截图、必要 Trace/录屏和运行时版本；凭据通过受限 grant/ref 进入，不进入普通日志和结果包。
↓
5

Outcome Verifier 判定

动作“没有报错”不等于成功。对 required validation 逐项验证；验证失败就停止或进入允许的修复逻辑，不能把失败素材包装成成功。
↓
6

受控运行时修复

仅允许 selector、frame、wait 等技术性小修复；不得更改业务目的、action type、输入、顺序、副作用或成功标准。每个 Patch 带原因、证据、范围与审计记录。
↓
7

素材编目与视频编辑

把录屏、动作后脱敏截图、步骤结果组织为 Asset Timeline Catalog；生成受字段锁约束的 DemoEditPlan，支持预览、调整和 FFmpeg 最终渲染。
↓
8

结果打包、交付与 ACK

生成 Recording Result Package，绑定源 Package ID、状态、验证报告、修复账本、视频和诊断；支持下载、复核、修订、保留策略和消费确认。

我负责的 Server 侧任务

你的核心职责可以概括为：把 App 的“已批准意图”可靠地变成“已验证结果”，并交付可用视频，而不是仅仅把脚本跑完。

1. 协议契约与兼容性

维护 Exchange、Execution Package、Browser Agent Outline、Result Package 的版本；提供 fixture、兼容矩阵和明确迁移策略。

2. Intake 安全门

完善身份、签名、摘要、加密引用、防重放、幂等、审批 Hash、域名和输出策略校验；确保非法包不能进入 Worker。

3. 任务状态机

维护 initialized/uploaded/accepted/queued/running/completed/failed/canceled/expired，保证重试、取消和终态幂等。

4. Runtime Router

按 runtime manifest 分派执行器，冻结旧运行时、推进 browser-agent-outline-v1，避免分支逻辑散落在业务代码。

5. Browser Agent 编排

编译 Stage、建立隔离上下文、执行政策守卫、目标解析、超时、资源回收和结构化事件审计。

6. Outcome Verifier

把成功标准结构化；实现执行前、逐步骤和执行后验证，保存决策证据，并确保验证失败不能被编辑层掩盖。

7. Repair Policy

限定允许修复的字段、风险级别、次数和证据要求；保留不可变原稿与 Patch Ledger，支持回放和责任定位。

8. 录制与脱敏

管理截图、录屏、Trace 的启停、遮罩与保留期；确保密码、Token、Cookie、Storage 和敏感输入不进入普通产物。

9. 视频编辑与渲染

维护素材目录、默认编辑计划、锁定字段、预览/最终渲染、静态截图成片、FFmpeg 错误归因与质量验证。

10. 结果与交付

生成可验证 Result Package，提供状态、下载、ACK、复核、修订与清理；保证结果和原输入、运行证据形成闭环。

11. 可观测性与 SLO

分阶段记录延迟、成功率、验证失败率、修复率、渲染耗时、队列等待、资源占用和错误码分布。

12. 测试与发布

契约测试、确定性 fixture、Worker 测试、真实页面 acceptance、失败注入、安全测试、版本回滚和容量验证。

推荐优先级

  1. P0：可信闭环。生产 Intake 加密引用、安装身份、审批/Hash、Outcome Verifier、终态和结果包全部贯通。
  2. P0：安全与隔离。域名/路由/动作政策不可绕过，凭据和敏感页面数据不落普通存储。
  3. P1：稳定性。队列、租约、幂等重试、超时回收、失败诊断、Worker 横向扩展。
  4. P1：媒体质量。素材时间线、预览、最终渲染、音频/字幕/品牌模板和结果 QA。
  5. P2：v2 探索与双证据融合。逐步由“执行 App Outline”演进到 Server 真实页面探索和冲突分类。

安全、隐私与审计设计

风险Server 控制对外回答要点
伪造或篡改执行包安装身份、签名、canonical digest、审批 Hash、nonce、防重放、TTLServer 不信任普通 JSON 自报身份，每个执行结果可回链到获批输入。
越权访问网页allowed domains/origins/routes、forbidden pages/actions、隔离上下文模型只能在政策围栏内提出候选，确定性守卫拥有最终否决权。
凭据泄露grant/ref、密钥封装、日志脱敏、遮罩、禁止保存 Cookie/Storage 明文凭据是短生命周期能力，不是执行包字段。
误判成功required Outcome Validation、执行前/后验证、失败诊断点击成功不是业务成功；只有验证通过才进入成功结果。
自动修复改变业务Repair Policy 白名单、原稿不可变、Patch Ledger只修技术漂移，不改业务意图、输入、副作用和成功标准。
敏感媒体长期留存分级产物、加密、retention、ACK 后清理、可审计删除保留策略是结果契约的一部分，而不是运维口头约定。

投资人可能提问与详细回答示例

点击问题展开。回答中的数据指标应在正式路演前替换为真实压测或客户数据，禁止把设计目标表述为既有业绩。

1. Server 到底解决了什么不可替代的问题？

示例回答：App 能理解产品和生成演示计划，但从计划到可信视频之间还有一个高风险缺口：网页会变化、选择器会漂移、动作不报错也可能没有产生业务结果、录制素材还要经过编辑和交付。Server 的价值是把这一段变成协议化生产流水线。它验证来源和审批，在隔离浏览器里执行，用 Outcome Verifier 判断真实结果，只允许低风险技术修复，最后把证据和视频绑定进结果包。因此我们卖的不是一次性的脚本生成，而是可重复、可审计的“verified demo production”。

2. 为什么不直接在 App 本地完成执行和剪辑？

示例回答：本地执行适合低成本预览，但不适合作为统一的企业交付权威。客户端环境差异大、容易离线、资源不可控，也难以统一安全策略、审计、版本和重试。Server 可以集中管理运行时版本、浏览器镜像、策略、渲染资源、状态和结果保留，同时让 App 保留业务理解与人机交互优势。我们仍支持本地开发验收，但生产结果由 Server 形成统一可信链路。

3. 你们和 Playwright、录屏工具或 RPA 有什么区别？

示例回答：Playwright 是优秀的浏览器执行基础设施，我们建立在它之上，但产品边界更高一层。传统脚本/RPA 关注“做动作”，我们还要验证动作代表的业务结果、限制自动修复不能改变意图、把每一步证据映射到视频素材，并通过版本化结果包交付。简单说，Playwright 是执行引擎之一；Cascade Server 是围绕业务授权、可信执行和媒体交付的控制面。

4. 网页 UI 经常变化，系统会不会非常脆弱？

示例回答：我们把变化分成两类。业务变化必须回到 App/审批方重新确认，Server 不擅自改；技术漂移，例如 testid、frame 或等待条件变化，可以由真实页面观察产生候选，再经过 Repair Policy Guard 判断是否属于允许范围。修复以 Patch 叠加在不可变原稿上并进入账本。这样既提高恢复率，又不会用“智能”掩盖业务语义被改变。我们会用 First-pass Success 和 Safe Repair Recovery 两个指标分别衡量基础质量和韧性。

5. 如何证明视频里的流程真的成功，而不是只录到了点击？

示例回答：每个关键动作都应带 Outcome Contract，例如元素可见、URL 状态、业务记录出现或指定状态变化。Server 在动作后运行 required validations；只有验证通过才把步骤标记为成功。验证报告、步骤事件和素材引用进入 Recording Result Package。编辑层不能把 failed step 变成成功，也不能通过剪辑隐藏 required validation 失败。这是我们和普通“操作录屏生成器”的核心区别。

6. 客户密码、Cookie 和产品数据会不会泄露？

示例回答：设计上不把明文密码、Token、Cookie 或 Storage 放进普通执行包。生产链路使用加密 payload reference 和安装身份，凭据应通过短生命周期 grant/ref 进入隔离 Worker。浏览器 Observation、日志和结果包只保存允许且脱敏的字段；敏感选择器在截图和录制时遮罩，媒体按保留策略清理。当前代码已经体现这些契约和本地安全边界，云 KMS、对象存储和多租户隔离是生产化重点。

7. LLM 或 Browser Agent 会不会执行危险操作？

示例回答：模型不拥有最终执行权。允许域名、来源、路由、禁用页面、动作类型、输入、资源上限和结果标准由确定性政策守卫执行；模型只能在边界内提出候选。高风险或业务语义变化不能由修复机制放行，必须回到外部授权。我们的安全模型是“模型建议、确定性服务裁决、证据系统验收”。

8. 系统如何支持规模化和高并发？

示例回答：架构天然按控制面和 Worker 面拆分。控制面负责 Intake、幂等状态机、队列、租约和结果索引；浏览器与渲染 Worker 是有资源配额的短生命周期任务，可按队列深度横向扩展。对象存储承载大媒体，数据库只存元数据和引用。当前仓库已经有运行时路由、状态和驱动边界，下一步生产化重点是持久队列、Worker 租约、容器隔离、容量调度和 P95 SLO 验证。

9. 单个视频的成本如何控制，毛利空间在哪里？

示例回答：主要成本来自浏览器时长、模型调用、视频编码和媒体存储。我们的策略是确定性解析优先、模型只处理不确定部分；执行证据和编辑素材复用；预览使用较低分辨率；最终渲染按需；失败尽早在 Intake 或 preflight 阶段拒绝，避免启动昂贵 Worker。核心单位经济指标是 Cost per Verified Minute，而不是每次 API 调用成本。正式数字会由真实 workload 的 P50/P95 采样给出。

10. 竞争壁垒是什么？别人也能拼接 LLM、Playwright 和 FFmpeg。

示例回答：单个组件都可以买到，壁垒在长期积累的跨层契约和反馈数据：业务动作与真实页面目标的对齐、结果验证规则、失败分类、允许修复策略、步骤证据到视频素材的映射，以及不同产品/版本下的恢复数据。这些决定稳定性、安全性和交付质量。随着任务增长，我们积累的是“什么情况下可以安全执行并证明成功”的结构化知识，而不是只积累 Prompt。

11. Server 出故障后如何重试，是否会重复执行有副作用的动作？

示例回答：上传和任务使用组织范围内的幂等键，状态机区分未启动、运行中和终态；Server 不会因为客户端重试就自动重复一个已开始或已结束的任务。对于有业务副作用的 Stage，还需要结合动作级幂等设计、前置状态观察和 Outcome Verification 决定恢复策略。生产化会使用 Worker lease、heartbeat 和 checkpoint：无法证明安全重放时，任务进入人工复核而不是盲目重试。

12. 如何做多租户隔离和企业合规？

示例回答：所有资源以 org/project/install/session/package 形成授权链，媒体和密钥引用必须带租户边界。生产目标是每任务隔离 Worker、最小权限网络出口、租户级密钥或 envelope key、加密对象存储、结构化审计、可配置 retention、导出和删除证明。合规认证本身需要独立项目推进；我们不会把架构控制直接宣称为已经获得某项认证。

13. 为什么需要自定义 Exchange Package，而不是普通 REST JSON？

示例回答：因为这是跨信任边界的可执行工作负载，不只是业务数据。Envelope 把发送者、组织项目、包类型、Schema、摘要、签名、nonce、有效期、加密引用、保留和执行窗口绑定起来；幂等和防重放也在同一契约内。普通 REST body 可以传字段，但很难形成可独立验证、可长期演进和可审计的执行授权载体。

14. 视频编辑为什么在 Server，而不是交给第三方生成式视频模型？

示例回答：产品演示首先要求真实性和可追溯性。Server 的默认编辑计划只使用已有、已验证的录制或动作后截图，锁定来源、步骤顺序和关键字段，FFmpeg 提供确定性渲染。生成式媒体可以作为受控增强层，例如片头或旁白，但不能替换产品执行证据。这样既可保证品牌和效率，也避免模型“创造”不存在的产品状态。

15. 当前最大的技术风险和未来 6—12 个月重点是什么？

示例回答：最大风险不是能不能跑通一次，而是跨产品、版本和租户稳定运行。近期重点有三类：第一，完成生产 Intake、密钥、对象存储、队列和 Worker 隔离；第二，用真实样本提升 verified completion、失败诊断和安全修复率；第三，把 v2 的 Server 探索与双证据融合逐步落地。我们会按阶段门槛推进：先保证可信闭环，再优化成功率和成本，最后扩大自主探索范围。

60 秒对外介绍话术

“Cascade DemoOps 把软件产品演示从人工录制变成可验证的自动化生产。App 负责理解客户产品、组织业务步骤并完成人审授权；Server 接收版本化的加密执行包，在隔离浏览器中按策略执行，用 Outcome Verifier 判断每一步是否真正产生业务结果，并只对 selector、frame、wait 这类低风险技术漂移进行可审计修复。执行证据随后进入受约束的视频编辑和 FFmpeg 渲染，最终以可追溯的结果包交付。我们的核心不是让 AI 随便操作网页，而是让企业能够安全、稳定、规模化地产出可信产品视频。”
